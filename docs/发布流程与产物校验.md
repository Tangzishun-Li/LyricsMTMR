# 发布流程与产物校验（结果度量）

> 起因：v0.3.2 / v0.3.3 / v0.3.4 的 `Upload to GitHub Release` 步骤失败，留下三个**空 release**；
> 同时 `SUFeedURL` 指向 `releases/latest/download/appcast.xml`，而 latest 稳定版没有 appcast，
> 于是自动更新对所有稳定版用户返回 404。根目录 `appcast.xml` 的 enclosure 还指向不存在的 `.dmg`。
> 这些都不是"构建失败"，而是"构建成功但用户拿不到"——单元测试永远抓不到。
> 本文件把"用户那端能不能拿到"变成机器可判定的结果。

## 1. 现在的链路

```
打 tag vX.Y.Z（或 gh workflow run publish.yml -f tag=vX.Y.Z）
  └─ publish.yml
       ├─ archive（universal，unsigned）
       ├─ zip + sha256
       ├─ DMG + sha256（仅发布 release 时生成，日常构建不产出）
       ├─ Sparkle 签名 → appcast.xml（预发布带 <sparkle:prerelease/>）
       │    └─ minimumSystemVersion 从包内 LSMinimumSystemVersion 读取，不写死
       ├─ gh release create/upload（可重入 --clobber）
       └─ verify_release.py --tag <tag> --download    ← 失败即 workflow 红
            正式版再校验 releases/latest 已指向新版本（最多重试 6 次）
  └─ release-health.yml（每天 01:17 UTC + release published）
       └─ verify_release.py --tag latest --download   ← 404/空资产每日哨兵
  └─ build-test.yml（push main / workflow_dispatch）
       ├─ test + build
       └─ package-smoke：archive + zip + Info.plist + Sparkle 嵌入 + 版本号↔tag
```

## 2. 本地命令

| 目的 | 命令 |
| --- | --- |
| 发版前冒烟（不签名，不含 DMG） | `make smoke` |
| 校验线上 latest 产物 | `make verify-release` |
| 校验指定 tag | `make verify-release TAG=v0.3.5-preview` |
| 重建根 appcast（派生文件） | `make rebuild-appcast` |
| 重建并读包内 Info.plist 纠正版本/最低系统 | `python3 LyricsMTMR/Scripts/rebuild_appcast.py --inspect-artifacts` |
| 只校验仓库内 appcast | `python3 LyricsMTMR/Scripts/verify_release.py --self-check` |

`verify_release.py` 会检查：zip/sha256/appcast 三个资产存在且非空（发布工作流另加 `--require-dmg`）→
feed 可下载 → appcast 可解析 → edSignature/length 在位 → tag 与 shortVersionString 一致 →
enclosure 可下载且大小匹配 →（`--download`）sha256 与 `.sha256` 资产一致、**解包后的
`LSMinimumSystemVersion` / `CFBundleVersion` / `CFBundleShortVersionString` 与 feed 声明逐项相等**。

## 3. 修复历史空 release

需要本地已登录 `gh`（仓库写权限）：

```bash
# 用 main 上的最新工作流，重新构建指定的历史 tag 并补传资产
gh workflow run publish.yml --ref main -f tag=v0.3.4

# 观察
gh run watch
# 或直接校验
make verify-release
```

补传成功后 `releases/latest/download/appcast.xml` 应返回 200，
`release-health` 也会从红转绿。

## 3.5 签名策略

- **发布前 ad-hoc 深度签名**：`publish.yml` 在打包前执行
  `codesign --force --deep --sign - --timestamp=none`，并断言 `codesign --verify --deep --strict` 通过。
  原因：xcodebuild 归档产物只有主二进制的 linker-signed，`Sparkle.framework` 等嵌套代码没有有效签名；
  下载后带隔离属性的 App 会被 macOS 判成“已损坏”，DMG 双击打不开（实测 `codesign --verify --deep --strict`
  报 `code object is not signed at all`）。
- **仍未公证**：Gatekeeper 仍会提示“未识别的开发者”，右键打开可用。
  要彻底免提示，需要 Developer ID Application 证书 + `notarytool` 提交 + `stapler` 装订，
  等具备付费开发者账号后再接入（本机目前只有 Apple Development 证书）。
- `package_smoke.sh` 与发布流程用同一套签名命令，CI 能在发版前发现“嵌套框架没签”。

## 4. 已知边界

- **预发布不更新 `releases/latest`**（GitHub 语义）：只发 preview 时，latest 仍指向上一个正式版。
  因此正式版必须自己把 appcast 传上去；历史上 v0.3.4 的空发布是唯一会 404 的情况。
- **未做 Apple 公证**：DMG 里的 App 仍未公证，CI 只能校验结构与签名，不能保证 Gatekeeper 放行；用户需右键打开。
- **DMG 只在发布时生成**：`build-test` 的打包冒烟不产出 DMG，避免每次 push 都跑 hdiutil。
- **根 appcast.xml 是派生文件**：由 `rebuild_appcast.py` 从真实 release 生成，
  只收录"release 真带 appcast 且 enclosure 资产存在"的条目，不要手改。

## 5. 修复记录与待办

**2026-11-14 已修复 v0.3.4**：用 `gh workflow run publish.yml --ref fix-release-chain -f tag=v0.3.4`
重建并补传，`releases/latest/download/appcast.xml` 从 404 变为 200，latest 正式版恢复
zip/sha256/appcast 三个资产。根目录 appcast 同步重建为 2 条真实条目。

过程中修掉的两个真实缺陷：
1. `gh release view --json` 没有 `isLatest` 字段 → 发布步骤 exit 1（v0.3.2~0.3.4 上传后的收尾步骤就是这个字段报错）；
2. `verify_release.py` 默认把"仓库根 appcast"也算进发布校验 → 产物已修好但文档未合并时误判；
   现改为 `--also-self-check` 显式开启。
