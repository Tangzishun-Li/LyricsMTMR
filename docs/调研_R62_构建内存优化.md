- 卡：t_2cf84cc1（r62-d，research-agents）；分支 lyricsmtmr/t_2cf84cc1-r62-d；2026-08-24 夜。
- 边界：只产报告不改源码；外部结论带 URL；对本仓结论带 文件:行号 或可复现实测口径。
- 背景：轨道文本_R62 §1 已实证「一开就卡死」= 多 worker 并发 xcodebuild 把 8GB 挤爆换页（E6/E7），锁脚本（r62-b，契约见轨道文本 §4.2）止血后，本报告回答「还能怎样让构建更省内存更快」。

- 测量方法：`scripts/measure_r62d.sh <label> <derivedDataPath> [xcodebuild 附加参数…]`（本分支新增，可复跑）：独立 `-derivedDataPath` 保证 clean 语义；后台每 0.5s 用 ps 快照求和 swift/clang/xcodebuild/ld 的 RSS 作为「构建进程内存峰值」，另以 `/usr/bin/time -l` 记 xcodebuild 主进程 max RSS；构建命令与轨道文本 §2 完全一致（scheme MTMR / Debug / CODE_SIGNING_ALLOWED=NO）。
- 局限：①wall 时间受文件系统缓存热度影响明显（同为全新 DD，首批 52.9s vs 热缓存复现 37.3s），跨组比较应以峰值内存为主指标；②RSS 快照粒度 0.5s，可能低估短命峰值；③实测期间系统 swap 常驻 5.8–6.7GB（当日多轮构建遗留），绝对值含系统噪声，趋势可信。

## ① xcodebuild 内存构成本仓实测（clean/incremental 峰值与耗时）

### 1.2 构成判读

- **峰值大头是 Swift 编译舰队，不是 xcodebuild 本体**：主进程 maxRSS 恒定 126–137MB，而构建进程总和峰值 1.3–2.0GB——差额即并发 swift-frontend/clang 舰队。clean 比 no-op 增量高出一个数量级（1818 vs 162MB），证明「省内存」的关键变量就是**同时存活的编译前端数量**。
- **峰值随 -jobs 单调上升**（#4→#3→#2）：j2 1273MB → j4 ~1820MB → j8 1955MB。-jobs 语义为「最大并发构建操作数」（`xcodebuild -help`：「specify the maximum number of concurrent build operations」，本机实拍输出存档于报告写作现场）。
- **j8 是双输**：最慢（57.9s）且最肥（1955MB）。
- **增量维度**：小改动重编一批 ≈1023MB/12s；no-op 地板 162MB/6.4s。INTEG 里程碑的「整体构建」若为 no-op 成本很低；真实增量约千兆级瞬时压力，与 clean 同量级风险。
- **机理注脚（重要残余风险）**：swiftc 驱动命令行自带 `-c -j8` 且**不随 -jobs 变化**（四组构建日志 grep 'builtin-SwiftDriver … -c -j8' 全部命中，含 j2 组；日志在 /tmp/r62d-clean-j4-rep-build.log 等）。且 j2 增量组亦观测到瞬时 10 个 swift-frontend 存活（warm 系列快照，因系统当时处于换页回填其峰值数字不可作基线，仅作并发结构证据）。⇒ **-jobs 只约束构建系统层调度，压不住 Swift 驱动内部并发**；单构建的内存下限由此被托高，这正是「同时在飞重型构建 ≤2」（轨道文本 §2）与锁脚本互斥必须坚持的结构性原因。
- 索引活动实证：普通 CLI build 也注入 `-index-store-path …/Index.noindex/DataStore`（clean-j4 日志 builtin-SwiftDriver 行），带索引构建后 Index.noindex 落盘 39MB（du 实测 dd-cj4r），整个 DD 366MB；库内 ~/Library/Developer/Xcode/DerivedData 下现存 **19 个 LyricsMTMR-* 目录，其中 12 个有实体积、合计约 3.8GB**（du 全量实测，最大单份 551MB）——多 worktree 多轮构建的 DD 堆积本身就是磁盘与内存外的隐性压力源（⑤节 P2）。

## ② -jobs 取值建议（8 核 M1 + 8GB 约束）

- **实测依据**：①节 #2/#3/#4——j2 比 j4 省 ≈30%、比 j8 省 35%，而耗时差距在缓存热度噪声内（j2 44.2s vs 首批 j4 52.9s vs 热缓存 j4 37.3s）；j8 同时最慢最肥。
- **建议：锁脚本 `MTMR_BUILD_JOBS` 缺省取 2**（当前契约缺省 4，轨道文本_R62 §4.2）。理由：8GB 机上单构建峰值从 ~1.8GB 压到 ~1.27GB，等于给「第二台在飞构建 + 前台 App」腾出约 550MB 余量——按轨道 §1 E6（free pages ≈110MB 即进入假死）的敏感度，这个余量正好覆盖一次前台启动的 RSS 需求（父卡 E2 实测本应用 RSS 65MB）。速度代价实测不可辨（缓存热度噪声 ≥ jobs 差异）。
- **禁止 -jobs 8**；仅在「确认机器独占且追求极限」时可临时 4。
- **边界说明**：-jobs 无法限制 Swift 驱动内部 `-j8` 舰队（①节机理注脚），因此 -jobs 是「调优」而非「护栏」；真正的护栏仍是锁脚本串行化 + 在飞 ≤2。若未来想把驱动内部并发也压下来，候选实验是给 swiftc 传驱动线程数（OTHER_SWIFT_FLAGS 注入 `-j 2` 类参数，属未公开稳定接口，**待确认**，建议单开 spike 卡验证后再定）。

## ③ 增量构建面候选（模块拆分/显式 API/SwiftUI 类型检查瓶颈）

- **R54 既有定位（只引用不复证）**：SwiftUI 类型检查总耗时 56.3s / 54,080 表达式，Top10 慢文件占 32%（KeyBindingTabView 3.4s、RibbonEditorView 3.2s、EditorSchema 2.9s、UnifiedSettingsWindowController 1.9s、StatusBarMenuView 1.3s 等），编译选项检查结论「Debug 已最优无需修改」。出处：logs/第54轮/构建性能分析报告_第54轮_t_bd3381c7.md:18（总结论）、:28（48s clean 基线）、:38-39（表达式数与总耗时）、:42-57（Top10 表）。
- **本轮补充的内存维度**：③节表格 #6/#7——增量重编一批峰值 ~1.0GB，no-op 地板 162MB。即「增量构建慢/胀」主要发生在真的触发了 Swift 模块重发射的时刻。
- **单 target 结构实证**：全 app 192 个 Swift 源文件 / 51,800 行在同一 native target（LyricsMTMR.xcodeproj/project.pbxproj:1135 与 :1154 为仅有的两个 PBXNativeTarget=app+MTMRTests；规模统计 find MTMR -name '*.swift'）。任何核心文件的接口变化都会触发整模块重发射——这就是「改一行、编一船」的结构性原因，也是增量峰值仍达 GB 级的原因。
- **候选 A（低成本，立即可做）：类型检查慢文件治理**——按 R54 清单对 Top 文件做显式类型标注/拆小 body（例如 EditorSchema.items static let 单表达式 1308ms，R54 报告 :59 起）。属代码微调，逐文件独立可合，不动架构；预期削的是 56.3s 类型检查大头（内存与时延同源：类型检查表达式就是 swift-frontend 的常驻工作量）。建议后续轮次按文件开小卡分批消化。
- **候选 B（高成本，远期）：target 拆分**（Core / Widgets / Preferences / LyricsIntegration 各自成 target）。收益：增量面物理隔离、并行度更细；成本：pbxproj 大手术 + 桥接约束（`-import-objc-header …/TouchBarPrivateApi-Bridging.h` 见 clean 构建日志；CBridge 目录 MediaRemoteMRBridge.dylib 由 shell 脚本单独编译，project.pbxproj:1280）。建议仅在前述候选收敛后立项。
- **候选 C（平台红利，前瞻）：Xcode 26 编译缓存**（LLVM CAS / COMPILATION_CACHE_ENABLE_CACHING 等，详见 ④-4）。本机 Xcode 16.4 不可用；升级后 clean/跨分支场景收益显著（外部数据 19%~55%），届时本仓「worktree 反复 clean 构建」的模式受益最大。
- **候选 D（零成本，随手做）：COMPILER_INDEX_STORE_ENABLE=NO**——①节 #5 实测峰值 -78MB（-4.3%）且 wall 更快；CLI 场景无人消费该索引（索引消费者是 Xcode IDE，IDE 有自己的索引体系），风险为零。已纳入 r62-b 锁脚本契约（轨道文本 §4.2「COMPILER_INDEX_STORE_ENABLE=NO（命令已含则不重复加）」），本轮提供实测背书。

## ④ 第三方方案评估（xcache/sccache 类；沙盒与签名兼容性）

1. **sccache（mozilla/sccache）— 不采用**。官方 README 明确支持列表为 gcc/clang/MSVC/rustc/NVCC/NVC++/hipcc/diab，**不含 swiftc**（https://github.com/mozilla/sccache ，README "Supported compilers" 段；页面存档于本次调研抓取）。本仓构建负载 99% 在 Swift，sccache 至多包住 CBridge 的单个 .m——收益趋近于零，不值得引入。Swift 社区实践同样仅把它用于编译器自身开发场景（https://forums.swift.org/t/using-sccache-to-speed-up-compiler-builds/29878 ）。
2. **XCRemoteCache（spotify）— 不采用**。三项硬伤对本仓致命：① 明确要求「The new Swift driver (introduced by default in Xcode 14.0) is not supported and has to be disabled」——本仓恰在新驱动上（构建日志 builtin-SwiftDriver 实证）；② 面向「CI producer + 多机 consumer + 自建 REST/S3 缓存服务」的团队架构，单人本地无收益；③ 不支持 SPM 依赖。（https://github.com/spotify/XCRemoteCache ，README Requirements/Limitations 段。）前置条件不满足，连沙盒试装都不必做。
3. **xcache 等社区小工具 — 无可靠出处，待确认**。常见被引的 xcache 仓库现已 404（https://github.com/pmusolino/xcache 实测 404）；其余检索命中均为个人博客级内容，不满足「带 URL 出处」的可靠性门槛。如有具体工具名可再评估，当前不下结论。
4. **Xcode 26 官方编译缓存（Apple 原生路线）— 前瞻项，升级后首选**。Xcode 26 引入基于 LLVM CAS 的编译缓存（`COMPILATION_CACHE_ENABLE_CACHING` / `SWIFT_ENABLE_COMPILE_CACHE` / `CLANG_ENABLE_COMPILE_CACHE`，Swift 目标默认配显式模块），外部实测本地缓存使 clean 提速 ~19%（SwiftPM 集成）至 ~55%（Xcode target 集成）（https://bitrise.io/blog/post/lifting-the-hood-on-build-cache-for-xcode ；https://medium.com/@saiprasanthamuluru/your-xcode-builds-are-doing-unnecessary-work-heres-the-fix-e0620f6690c1 ）。已知坑：bridging header 绝对路径导致跨机缓存失效、宏相关偶发 miss（https://forums.swift.org/t/about-swift-shared-cache-across-machines/81850 ）。本仓有自定义 bridging header（TouchBarPrivateApi-Bridging.h），跨机共享前需按该帖方案验证（PREFIX_MAPPING 项）。
   - **签名兼容性评估（覆盖 ④ 总要求）**：编译缓存类方案缓存的是编译中间产物（.o / swiftmodule / CAS blob），最终链接与 codesign 仍在构建末端原生完成，产物签名机制不变，无重签风险（XCRemoteCache 甚至专门处理 dSYM/debug symbols 一致性，见其 README "Debug symbols" 段）。真实风险在别处：①缓存陈旧/hermetic 性（绝对路径、模块缓存路径不一致导致假 miss 或错配）；②远端缓存的供应链信任（缓存投毒）；③本机代理环境（Clash 7890）下远端同步的稳定性。对单机本地场景，①②③均可控或不适用。
5. **结论**：在 Xcode 16.4 现状下，**没有值得引入的第三方缓存工具**；资源应集中在锁脚本纪律（-jobs 2 + 串行 + noindex）与 R54 慢文件治理。Xcode 26 到位后走官方 CAS 路线，不走第三方。
