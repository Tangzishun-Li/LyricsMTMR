# 未完成组件归档（Widget Availability）

> 起因（2026-11 体检）：项目登记了 114 个组件，但默认预设只用 15 个，且部分组件
> "能编译、没验收"。广度淹没了主场景（歌词），新用户也无法判断哪些能放心用。
> 本文件定义组件的成熟度分级、当前归档清单，以及晋升/降级的操作方式。

## 1. 三级定义

| 状态 | 组件库表现 | 旧预设表现 | 适用 |
| --- | --- | --- | --- |
| `stable` | 默认可见、可添加 | 正常渲染 | 已验收、失败态有处理 |
| `experimental`（未完成） | 默认隐藏；编辑器组件库打开"显示未完成组件"后可见，带**未完成**角标 | 正常渲染 | 已接入但未端到端验收 / 依赖外部配置 / 只做了数据接入 |
| `archived`（已归档） | 组件库**永不出现**，不能新增 | 正常渲染 | 功能确认不可用、需按新接口重做 |

关键约束：**归档只影响"新增入口"，不影响解析与渲染**。
`WidgetAvailabilityTests.testArchivedTypesStillParseFromPreset` 钉住了这一点——
否则用户旧预设里的组件会被静默丢弃。

## 2. 当前清单

实现见 `LyricsMTMR/MTMR/Core/WidgetAvailability.swift`。

### experimental（未完成 / 玩具向，11 个）

| 类型 | 原因 |
| --- | --- |
| `packageTracker` 快递 | 依赖第三方快递查询接口，可用性随提供方变化（README 已注明） |
| `expenseTracker` 记账 | BeeCount 同步只做了单测与静默回退，GUI 端到端未真机验收 |
| `bilibiliFeed` B 站 | 抓取式数据源，接口变动即失效，失败态未打磨 |
| `pixelPet` | 娱乐向，无验收标准 |
| `httpCodes` / `latexSymbols` / `colorConvert` / `base64Tool` / `jsonFormatter` / `hashCalc` / `uuidGen` | 工具箱类小工具：能跑，但无验收标准、不承担主场景 |

### archived（已归档）

| 类型 | 原因 |
| --- | --- |
| `homekitScene` 智能家居 | HomeKit 授权 + 场景配置链路未验收；暂不提供新增入口 |

> 当前口径：palette 共 97 个类型，默认可用 **85** 个（97 − 11 实验 − 1 归档）。
> README 的"当前可用 85 种"由 `ReadmeWidgetCountTests` 与
> `EditorSchema.pickableTypes(includingUnfinished: false).count` 绑定，改清单必须同步改文案。

## 3. 晋升 / 降级怎么改

1. 编辑 `WidgetAvailability.swift` 的两个集合（只写字面量类型名）。
2. 同步更新本文件 §2 的表格。
3. 跑 `WidgetAvailabilityTests`：它会校验
   - 两个集合不重叠；
   - 集合里的类型名必须真实存在于 `EditorSchema.supportedTypes`（防手滑写错导致静默失效）；
   - 组件库过滤后的数量关系正确；
   - 归档类型仍能被预设解析。
4. 晋升为 `stable` 前，至少要有一次"真机 + 空态/失败态"观察记录（写进 `logs/` 或本文件）。

## 4. 为什么不直接删

- 删类型会破坏解析链（`ItemType`/`ItemTypeRaw`/注册表/工厂 4 处穷尽 switch），
  且用户旧预设直接报错或丢组件。
- 归档是"产品层收缩"，不改代码层注册；想真正删除时走单独的删除轮次（参照 R63 死代码簇做法）。

## 5. 与"114 个组件"文案的关系

README 现在仍写"114 种"，但组件库底部显示的是**当前可用数量**
（`EditorSchema.pickableTypes(includingUnfinished:)`），打开开关后才是全量。
后续如果继续收敛，应同步改 README 口径，避免"宣传 114、实际 110"的偏差。
