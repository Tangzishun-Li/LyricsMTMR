1. **GitHub Releases 全量仅 2 枚**：v1.0.0（首个正式发行版，published 2026-07-29T19:13:19Z）+ v0.8（预发布，published 2026-08-09T19:16:32Z）。v0.9~v0.26 从未以 Release 存在过。

3. **Info.plist 版本号变更史（264 提交全量扫描）**：自建仓初始提交 ddde2bde（2026-05-22）起即 0.27/452，恒定为 0.27/452 跨越 263 个提交（含 v1.0.0 与 v0.8 两个 tag 指向的提交），直至 round24 收口 82d2dc1（2026-08-13）才升为 0.28/453——全仓库版本号仅有 0.27/452 与 0.28/453 两个状态。

5. **README 处理决策**：采用**方案甲**——更新日志区补「版本史说明」段如实记录考古结论（v0.8/v1.0.0 为唯一正式发布记录、v0.9~v0.26 无任何 Release/tag 实证、更新日志自 v0.27 起按轮次补记），信息透明零虚构，与第 24 轮 B 卡「未虚构中间版本史」原则一致。

## 五、v0.9~v0.26 缺失段性质结论

**结论：v0.9~v0.26 从未以 Release、git tag 或 Info.plist 版本号任何形式存在过——它是更新日志编号序列中的空洞，不是被删除的历史，也不是未同步 README 的既有发布。**

论证链：

1. **Release 侧**：GitHub Releases API 全量仅 2 枚（v1.0.0、v0.8），API 返回无分页无 draft，不存在「有 Release 但未同步 README」的隐藏项；
2. **tag 侧**：git tag 全量仅 3 枚，无 v0.9~v0.26；即便有被删除的 tag，Release API 的 published 记录也不会消失（GitHub 删除 tag 不删 Release），故「tag 存在但被删」不成立；
3. **工程版本号侧**：264 提交全量扫描版本号仅 0.27/452、0.28/453 两个状态，Info.plist 从未出现 0.9~0.26 任一值；
4. **README 侧**：更新日志现存条目序列为 v0.28（当前开发版本）→ v0.27（第 13~18 轮快照）→ v0.8（预发布）→ v1.0.0，v0.9~v0.26 从未在 README 中出现过（第 24 轮 B 卡核对时确认）；
5. **成因解释**：项目以「第 N 轮」为真实迭代编号（iteration-log 体系），README 营销版本号仅用于发布快照——v0.8 预发布（2026-08-09）后，下一批迭代能力直接以「v0.27」名义登记（第 19 轮 README 补登时 Info.plist 恰为 0.27，索性借用了工程版本号），编号从 0.8 直接跳到 0.27，中间 18 个号从未被任何产物占用。
