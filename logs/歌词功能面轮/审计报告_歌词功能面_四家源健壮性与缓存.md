# 审计报告_歌词功能面_四家源健壮性与缓存

> 第 52 轮 / 子任务 A（歌词功能面轮）· 分支 `lyricsmtmr/t_33d5c9b0-a-kugou-migu-qqmusic`
> 审计对象：`LyricsMTMR/MTMR/LyricsIntegration/` 下 Kugou / Migu / QQMusic / NetEase 四家歌词源
> 结论要点：① 四源失败路径核清（超时均有界 10s、显式重试均为 0、失败语义各异但均有兜底）；② Kugou/Migu/QQMusic 补上歌词 LRU 缓存（抽公共容器，容量 32，键=歌曲唯一 id）；③ 命中/回源经既有 AppLog.lyrics 可辨，未引入新依赖。

## 0. 背景与取证

- 任务 t_a30596ce 点名「NetEase 做了缓存，其他三家呢？」。实测：改动前 `grep -n "cache|Cache"` 于 Kugou / Migu / QQMusic 三个 Provider 文件 0 命中；NetEaseProvider.swift:32 已有 `lyricsCache = LyricsLRUCache(capacity: 32)` 且 16 处缓存语义引用。
- 后果：切歌后切回近期歌曲，Kugou/Migu/QQMusic 每次重新请求网络并重新解密/解析（KRC 解密、QRC 三重 DES 解密、LRC 解析），失败亦无重试——歌词功能面空白。

### 1.5 审计结论（四源横向）

1. **超时**：四源全部经 `URLSessionConfiguration.timeoutIntervalForRequest = 10` 有界（文件:行号见上表），无悬挂请求；单一报表口径成立。
2. **重试**：四源显式重试均为 0。系统级兜底 = `LyricsSearchService.searchLyrics` 多源并发扇出（LyricsSearchService.swift:62-92，失败 provider 被 do/catch 跳过，其他源继续产出）；QQ 另有双搜索 API 冗余。R44/R45 网络重试治理对象是 widget 层，歌词层将「失败无重试」登记为已知取舍（下方风险点）。
3. **失败语义**：search 层普遍「空结果从宽」（不毒化整体搜索）——Migu 非 JSON 有日志、Kugou 静默空、QQ 双路冗余；fetch 层「缺歌词/解析失败」用专属 Error 区分（noLyrics / parseFailed），上层 do/catch 可辨。
4. **翻译/假名**：仅 NetEase 提供 fetchTranslation/fetchRomaji，且 try? 吞掉所有失败（:148-202），现状核清：增强面尽力而为、失败不可观测——不新增改动（属 R52 范围外保守），登记观察项。
5. **缓存**：改动前仅 NetEase 有（容量 32）；本次补齐三家（见 §2）。

## 2. 缓存补齐方案

- **抽公共容器**：新增 `LyricsMTMR/MTMR/LyricsIntegration/LyricsLRUCache.swift`——`final class LyricsLRUCache<Key: Hashable>`（internal，线程安全串行队列，条目字典 + MRU 序数组，与 NetEase 原实现逐语义等价，容量下限 max(1,·)）。NetEaseProvider 内嵌类删除，改 `typealias LyricsLRUCache = LyricsMTMR.LyricsLRUCache<Int>`（模块限定别名，`NetEaseProvider.LyricsLRUCache` 路径原样可编译，NetEaseLRUCacheTests 零修改兼容）。
- **四源接入**（键 = 歌曲唯一 id，容量统一 32）：

| 源 | 缓存键 | 声明位置 | 命中日志 | 成功回写 |
|----|--------|----------|----------|----------|
| Kugou | hash（sourceId="hash\|accessKey"，krcs 凭 hash 即可解析） | KugouProvider.swift:40 | `Kugou.fetchLyrics: cache HIT hash=` :82 | :101 |
| Migu | copyrightId（即 sourceId） | MiguProvider.swift:40 | `Migu.fetchLyrics: cache HIT copyrightId=` :81 | :116 |
| QQMusic | songMid（即 sourceId） | QQMusicProvider.swift:25 | `QQMusic.fetchLyrics: cache HIT songMid=` :95 | :129 |
| NetEase | songId (Int) | NetEaseProvider.swift:39 | `NetEase.fetchLyrics: cache HIT songId=` :89 | :121/:131/:140 |

- **内存压力兜底**：四源各具 `clearLyricsCache()`；AppDelegate.applicationDidReceiveMemoryWarning 四源同清（AppDelegate.swift:86-89，沿用 ITER-2 兜底语义）。
- **命中观测（需求 3）**：既有观测机制 = AppLog.lyrics（os.Logger，subsystem **com.lyricsmtmr.LyricsMTMR**，AppLog.swift:61-64）。四源 HIT 均为同一格式 `cache HIT`，Console.app 按 subsystem 过滤即可分辨「命中 / 回源」；未引入任何新依赖。
- 三源缓存声明由 `private` 放宽为 `internal`（注释注明，供 LyricsProviderCacheTests 预置/核对）；NetEase 维持 private（其单测走容器别名路径）。

## 7. 风险点 / 遗留登记

1. **歌词源显式重试为 0**（四源共点）：现状依赖系统级多源扇出 + QQ 双 API 冗余；单项源瞬时故障时该源本轮结果为空但不阻塞其他源。**候选**：后续轮可为 fetch 失败加 1 次单源重试（对齐 R44/R45 widget 层治理），本卡未做（超时 10s 有界 + 扇出兜底已可接受）。
2. **NetEase fetchTranslation/fetchRomaji 失败不可观测**（try? 吞错，:148-202）：增强面尽力而为属可接受取舍，登记为观察项，本次不动。
3. **三源缓存命中依赖歌曲唯一 id 稳定**：Kugou 键=hash（krcs 凭 hash 即可解析 accesskey，键稳定）；若上游将来改键生成规则需同步（低概率）。
4. 四源各 32 容量 = 至多 128 个 SimpleLyrics 常驻内存，均为小解析对象，且有内存警告兜底清空路径。
