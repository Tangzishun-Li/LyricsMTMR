## 〇、执行摘要

**现状**：日常运行中的 LyricsMTMR（PID 971，Debug 构建，已跑 25h+）实测 **15.4% CPU + 304MB 物理内存（peak 322MB）**，用户感知为"程序性能消耗很大"。

**根因（一句话）**：打开过一次设置窗口后**关窗 ≠ 释放**——`AppDelegate.swift:143` 强持有窗口控制器，配合 `UnifiedSettingsWindowController.swift:437-441` 全项目唯一 `repeatForever` 动画，驱动一棵 21-tab 的"夜店风"SwiftUI 视图树在**已关闭的窗口里以 60fps 持续离屏渲染**：这就是 ~15% CPU 的 93% 和 136MB CoreAnimation（占内存 45%）的 100% 来源。

**结论**：三路调查交叉印证，全部优化项均为**生命周期 / 频率 / 缓存 / 配置**类改动，**无结构性重构、无行为变更**。仅实施 A 档（安全低风险，8 项）即可回收 **~15% CPU + ~130-170MB 内存**；全部落地后日常 CPU 预计 ~1-2%、内存 ~150MB 内，同时修复 3 个用户可见小缺陷（歌词滚动回跳、暂停空转、脚本轮询拖系统负载）。

| 指标 | 当前 | A 档落地后 | 全部落地后 |
|---|---|---|---|
| CPU | 15.4% | **< 3%** | ~1-2% |
| 物理内存 | 304MB | **~150-170MB** | ~150MB 内 |
| 歌词滚动 | 0.25s 回跳 + 暂停空转 | 顺滑、暂停即停 | 同左 |

### 2.2 CPU 路证据

- `sample` 3s 快照：**378/2543 采样 ≈ 15%** 落在 `SwiftUI.DisplayLink → NSHostingView.startAsyncRendering → ViewGraph.updateOutputsAsync`——60fps 渲染一棵**已关闭**的窗口（System Events 查无 window）。
- 主线程 2526/2543 采样停在 mach_msg（空闲等待）→ 主线程不忙，消耗全在幽灵渲染。
- 歌词引擎 0.25s playbackTimer（4Hz）回调轻量、启停正确 → **必须保留**（CPU 报告 §四）。
- perl run.pl 桥 0% CPU（纯事件驱动 CFRunLoop）→ 健康。

## 三、根因链（一图流）

```
打开一次设置窗口（哪怕 1 秒）→ 关闭
   ↓
AppDelegate.swift:143 强持有 unifiedSettingsController（全文件无置 nil 路径）
   ↓
windowWillClose（UnifiedSettingsWindowController.swift:133-137）只清 weak static current + isVisible 标志
   → 窗口 / NSHostingView / 整棵 SwiftUI 视图树永不释放
   ↓
:437-441 全项目唯一 repeatForever 动画（Deck.Background 两个带 .blur(radius:5) 的 RadialGradient 漂移）
不订阅任何可见性状态 → 永不停止（对比 Equalizer :1113、歌词预览已做 paused，唯独漏了它）
   ↓
SwiftUI DisplayLink 以 60fps 持续渲染不可见窗口 = 15% CPU（sample 实锤）
   ↓
离屏渲染不断产生 CA backing store / IOSurface + 21 tab 图层树全量驻留
（SettingsTabCache :886-892 全缓存 + ZStack :1119-1127 全挂载 + 19 处 .shadow 离屏层）
= 136MB CoreAnimation / 1030 regions
```

**一句话：关掉设置窗口 ≠ 释放设置窗口。**窗口带着整棵"夜店风"图层树和永不停歇的动画在后台偷偷渲染，CPU 和内存同时被它吃掉。

## 四、优化措施详表（按风险从低到高；档内按收益排序）

> 每项均含：**改动点 / 预期收益 / 验证方式 / 是否影响正常使用**。B、C 档额外给出**替代方案 / 回滚方案 / 最小化变更策略**。

### A 档 · 安全低风险（行为无感，可直接实施）

#### A1. 关窗即释放设置窗口（最大单项）
- **改动点**：`AppDelegate.swift:143` 改 `private weak var unifiedSettingsController`；或在 `UnifiedSettingsWindowController.swift:133-137` windowWillClose 里回调置 nil（openSettings :157 的 nil 判断会自动重建）。
- **预期收益**：**~15% CPU 归零 + ~170MB 内存回收**（136MB CoreAnimation + SwiftUI 视图图/缓冲大头 B/C/E/F/L 的大部分）；DisplayLink 随窗口释放自然停止。
- **验证方式**：改后开一次设置再关闭 → `footprint <pid>`：CoreAnimation 136MB → 几十 MB；`heap <pid>`：`NSHostingView<SettingsRootView>` / AGSubgraph 消失；`sample <pid> 10`：SwiftUI.DisplayLink 采样归零。
- **是否影响正常使用**：否。窗口每次打开都是全新创建（含配置导入逻辑 :937 仍会触发）；唯一注意点：关窗未保存的改动——windowShouldClose :139-157 已有保存提示，**不受影响**。

#### A2. Deck.Background 动画挂可见性暂停
- **改动点**：`UnifiedSettingsWindowController.swift:437-441` repeatForever 前加 `paused: !windowState.isVisible`（**复用 :1113 Equalizer 的现有模式**）；或 `onDisappear` 里停止动画。
- **预期收益**：窗口不可见时 60fps 渲染归零（与 A1 互为保险：A1 管释放，A2 管"窗口还开着但隐藏"的路径）。
- **验证方式**：最小化窗口 / 切 Space → `sample` 无 DisplayLink；恢复可见动画正常。
- **是否影响正常使用**：否。窗口可见时行为与现状完全一致。

#### A3. 两个 RadialGradient 的 blur 改静态
- **改动点**：`:427, :435` 两处 `.blur(radius: 5)` 改为预渲染静态模糊纹理（启动时渲一次），动画只做 opacity/transform。
- **预期收益**：24~30MB backing 常驻消除 + 每帧 blur 重算消除。
- **验证方式**：`footprint` 看 CA 区再降；目视设置窗口背景与修复前几乎无差。
- **是否影响正常使用**：基本否。模糊半径固定 5、输入是缓慢漂移的渐变，静态化后观感差异极小；若用户对背景动效敏感，可跳过此项（A1+A2 已回收大头）。

#### A4. SettingsTabCache 加 LRU（3~5 tab）+ 暴露 removeAll()
- **改动点**：`:886-892` 缓存字典改为 LRU 淘汰（保留最近 3~5 个 tab），并暴露 `removeAll()` 给 A8。
- **预期收益**：窗口打开期间驻留的视图图从 21 tab 缩至活跃 tab（约省 10-15MB）；窗口常开场景收益明显。
- **验证方式**：开设置翻 10+ tab 再回首个 tab → `heap` 中视图图节点数不随 tab 数线性增长。
- **是否影响正常使用**：否。重开 tab 会重新构建视图（首次打开略慢几十 ms，无感）。

#### A5. marquee 三修：暂停即停 + 防 0.25s 回跳 + 60→30fps
- **改动点**：`LyricsTouchBarItem.swift`：① 暂停分支 :279-285 补 `stopMarqueeTimer()`（修缺陷 A）；② startMarquee :316-321 加"timer 已存在则复用"判断，仅行切换时重建（修缺陷 B 回跳 + 消除每 0.25s timer 重建）；③ `MarqueeMetrics.fps` 60→30（:25）。
- **预期收益**：~1-2% CPU + 修复用户可见的滚动回跳 + 暂停播放后 CPU 明显下降。
- **验证方式**：播放普通 LRC 歌曲（无逐字时间标签）→ 观察滚动平滑无回跳；暂停 → `sample` 确认 marquee 相关采样消失。
- **是否影响正常使用**：否，纯改进。30fps 在触摸条（约 1/3 屏宽）上肉眼无差。

#### A6. KaraokeLabel 缓存 fullTextWidth / intrinsicContentSize，ruby CTLine 预计算
- **改动点**：`KaraokeLabel.swift`：:167-173 fullTextWidth 与 :158-164 intrinsicContentSize 按行缓存（同文件 :129-156 `_ctFrame` 已有缓存模式可复用）；:465-501 ruby 布局改为预计算 CTLine，draw 只做 CTLineDraw（去掉 :475-483 while 收缩循环的每轮重建+测量）。
- **预期收益**：~0.5-1.5% CPU + MALLOC 瞬时对象抖动显著下降（30fps × 每字形 × 多轮测量的分配消除）。
- **验证方式**：播放带逐字时间标签歌曲 + 开启注音 → `heap` 观察 CT 对象不再每帧翻倍；目视渲染结果逐像素一致。
- **是否影响正常使用**：否。30fps 扫光效果本体保留（这是视觉需求，**必须保留**），只去掉其上的重复计算。

#### A7. 移除 UserDefaults synchronize()
- **改动点**：`AppSettings.swift:239-251`（:247）删除 `synchronize()` 调用（系统自动持久化）。
- **预期收益**：低频路径的同步刷盘消除（微收益，顺手）。
- **验证方式**：改设置项 → 杀进程重开 → 设置保留。
- **是否影响正常使用**：否。

#### A8. 实现 applicationDidReceiveMemoryWarning
- **改动点**：`AppDelegate.swift` 新增内存警告处理：SettingsTabCache.removeAll() + CoverCache.memoryCache 清理 + URLCache 清理。
- **预期收益**：系统内存压力时兜底释放（当前 0 响应）。
- **验证方式**：`sudo memory_pressure -S -l warn`（或 `vm_stat` 观察）→ 确认缓存被清。
- **是否影响正常使用**：否，纯新增兜底。

### B 档 · 低风险需观察（行为/口径有轻微变化，或需人工决策）

#### B1. 日常改用 Release 构建
- **改动点**：不改源码。`Scripts/build.sh:10` 默认参数改 Release（或日常运行 `xcodebuild -configuration Release` 产物 / `Release/LyricsMTMR.xcarchive` 内 app）；Debug 仅开发调试用。
- **预期收益**：Swift `-O` 优化下 60fps marquee/karaoke/幽灵渲染路径每帧成本再降 **30-60%**（在 A 档之上叠加）；`#if DEBUG` 代码（AppLog.debug 等）裁剪。
- **验证方式**：跑 Release 产物，逐项过一遍日常功能（歌词、设置、脚本组件、股票、更新检查）。
- **是否影响正常使用**：轻微——构建产物变了。Release 与 Debug 行为差异极小（无 DEBUG 分支功能、断言关闭）。
- **替代方案**：不改 build.sh，仅本次打包用 Release；或先并行安装 Release 版用 1-2 天观察再切换。
- **回滚方案**：直接跑回原 DerivedData Debug 产物，零成本。
- **最小化变更策略**：源码零改动，只动构建产物与脚本默认参数。

#### B2. CPU%/MEM% 脚本轮询调优（配置级改动）
- **改动点**：用户 items.json：① CPU% 组件脚本 `top -l 2 -n 0 -F | egrep | awk` 改为 `ps -A -o %cpu | awk` 单次快照（亚秒级）；② 与 MEM% 组件合并为一个脚本一次取 %cpu+%mem；③ 两个组件 `refreshInterval` 5→30s。
- **预期收益**：消除 ~40% 占空比的系统采样子进程（每 5s 一次 2s 存活），fork 频率降 ~12 倍；静息 CPU 再降 1-3%、IO 显著减少、系统负载读数不再虚高。
- **验证方式**：改后观察 CPU% 显示数值正常刷新（口径由"采样平均"变"瞬时快照"，数值略波动属预期）；`ps` 观察无 2s 级子进程周期出现。
- **是否影响正常使用**：轻微——显示数值口径变化（瞬时值 vs 平均值，均正确，只是含义不同）。
- **替代方案**：只改 interval 5→30s，脚本不动（零口径变化，收益减半）。
- **回滚方案**：`~/Library/Application Support/LyricsMTMR/items.json` 改前先 `cp` 备份，回滚即还原。
- **最小化变更策略**：先做③（仅间隔），确认无感后再做①+②（脚本内容）。

#### B3. 股票组件非交易时段降频
- **改动点**：`StockBarItem.swift:78-84` 定时器逻辑：非交易时段（盘前/午休/收盘后/周末）interval 提到 60s 或暂停；或用户配置 `chartMode` 关闭分时图。`refreshInterval` 的 clamp（:40，≥5s）需配合调整。
- **预期收益**：休市时省 2×HTTP/10s + 主线程全图重绘（分时图数据休市恒定，重绘纯浪费）；交易时段行为不变。
- **验证方式**：休市时段观察 `lsof -p <pid> | grep TCP` 无周期连接；`sample` 无重绘采样。
- **是否影响正常使用**：交易时段无感；休市时段数据刷新变慢（60s，无实际影响——数据本就不变）。
- **替代方案**：只把 interval 10→30s（分钟线数据 1 分钟才变，30s 足够），不做时段判断，简单安全。
- **回滚方案**：改回 interval 10s。
- **最小化变更策略**：先做替代方案（30s），确认无感后再评估时段判断。

#### B4. Sparkle 更新源修正或移除
- **改动点**：`Info.plist:111` `SUFeedURL` 改为 fork 自己的 GitHub Releases appcast（`https://github.com/Tangzishun-Li/LyricsMTMR/releases/latest/appcast.xml`，publish.yml 已有发布流）；或经用户确认后整体移除 Sparkle（`AppDelegate.swift:146` lazy updater + 菜单项）。
- **预期收益**：消除"原版 build > 452 时错装原版 MTMR"风险；手动检查更新省 6.5s 网络往返；更新通道复活（走自己 Releases）。
- **验证方式**：`curl <新 feed>` 返回 200 且版本号 ≥452；菜单"检查更新"行为正常。
- **是否影响正常使用**：是（决策项）——影响更新机制本身。当前自动检查已关（SUEnableAutomaticChecks=0），日常无感，但手动检查路径会变。
- **替代方案**：保持现状 + 关闭/移除"检查更新"菜单项（最小改动止血）；或只改 SUFeedURL 不动其它。
- **回滚方案**：还原 Info.plist 的 SUFeedURL（改前备份 plist）。
- **最小化变更策略**：先只改 SUFeedURL 指向 GitHub appcast（一处字符串）；移除 Sparkle 是更重的决策，留给用户单独定。

### C 档 · 较高风险（涉及核心交互 / 观感，需谨慎；均含替代、回滚、最小化策略）

#### C1. 切应用全量重建加快速路径
- **改动点**：`TouchBarController.swift:448-497` `updateActiveApp` 默认分支加 `guard`（如 `appDidChange` 判断 / `touchBarIsBuilt` 短路），同一应用重复激活不再走 `prepareTouchBar()` → `createItems()`（:623-682）全量销毁重建。
- **预期收益**：每次前后台切换的主线程一次性重建（数 10ms 级卡顿）消除；连锁副作用消失（歌词 item 重新订阅、AppleScript item 重新编译脚本、定时器全部重建）。
- **是否影响正常使用**：**是潜在风险项**——guard 条件写错会导致 Touch Bar 不随应用切换更新（核心功能）。**注意**：当前用户已开 `freezeOnAppSwitch=1`（defaults 实测），该项影响已受控；此修复主要惠及默认配置（freezeOnAppSwitch=false）用户，属代码健壮性修复。
- **替代方案**：保守版——仅当"目标 app 与当前相同且 items 已构建"时短路，`appDidChange` 为真时仍走全量路径（即只消除"同一 app 反复激活"的重复重建，不碰切换逻辑）。
- **回滚方案**：删除 guard 即恢复原行为；改动局限于一个函数，`git revert` 即可。
- **最小化变更策略**：先做替代方案（一行 `guard`），配合 freezeOnAppSwitch=1 用户实测无回归后再考虑放宽。

#### C2. 设置窗口 isVisible 全量可见性通知（可选加固）
- **改动点**：`UnifiedSettingsWindowController.swift:135-170` 现有通知集（windowWillClose / didBecomeKey / didMiniaturize / didDeminiaturize）扩展监听 `NSWindow.didOrderOut` / `willMoveToWindow`，任何隐藏路径都复位 isVisible。
- **预期收益**：根治非标准隐藏路径（orderOut / 切 Space 等）的离屏动画继续跑。
- **是否影响正常使用**：潜在风险——通知时机/状态机复杂，误复位会让可见窗口动画停摆。
- **重要前提**：**A1+A2 落地后此问题自然消失**（窗口关了即释放，动画随可见性暂停），本项降级为防御性加固，可做可不做。
- **替代方案**：不做；或只补 `windowDidResignKey` 一个通知的保守版。
- **回滚方案**：恢复原通知集（改动局限于 :135-170）。
- **最小化变更策略**：先验证 A1+A2 效果，若 24h 实测无幽灵渲染则跳过本项。

#### C3. 削减 19 处 `.shadow(` 离屏层（观感决策）
- **改动点**：重点削减最重的 Card :472 / Pill :548 / NavItem :1212 等处的 shadow（每处一个离屏 shadow 层），改小 radius / 改预渲染 / 移除。
- **预期收益**：CA regions 进一步下降（A1 之后 shadow 层随窗口释放，此项仅影响窗口**打开期间**的常驻）。
- **是否影响正常使用**：是（观感）——阴影是设置窗口设计系统的一部分，视觉有可感知变化。
- **替代方案**：只削减 2-3 处最重的（Card 等），或 shadow radius 减半；或保留不动（A1 已回收大头，此项纯锦上添花）。
- **回滚方案**：恢复对应行。
- **最小化变更策略**：与 A3 一起做一次视觉对比（截图前后对照），由用户拍板保留哪些。
