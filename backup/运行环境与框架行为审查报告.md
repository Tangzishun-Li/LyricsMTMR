## 1. 环境与构建配置

### 1.1 ⚠️ 日常运行的是 Debug 构建（高优先级）
- `Scripts/build.sh` 默认 `-configuration Debug`（build.sh:10）；用户实际运行的正是 DerivedData 里的 Debug 产物。
- 影响：Swift `-Onone` 无优化（渲染/布局/JSON 解析全部裸奔），`#if DEBUG` 代码全量激活（AppLog.debug），SwiftUI DisplayList 更新、CoreText 布局等每帧成本被放大数倍。
- **方案**：日常使用改跑 Release 产物（`xcodebuild -configuration Release` 或直接用 `Release/LyricsMTMR.xcarchive` 内的 app）；Debug 仅用于开发调试。
- **预期收益**：对 60fps marquee/karaoke/幽灵窗口渲染路径，通常再降 30–60% 的每帧 CPU（在 P0-1 修复之上叠加）。

### 1.2 环境变量 / 启动参数
- 全仓仅 1 处读取运行时环境变量：`XCTestConfigurationFilePath`（AppDelegate.swift:33，CI 跳过硬件初始化）——正确。
- run.pl 支持 `--id` / `--debug-dump`，但 MediaRemoteAdapter 启动监听时**未传任何 flag**（MediaRemoteAdapter.swift:49），debug 通道未开启。
- 无 UserDefaults/启动参数形式的 debug 开关。干净。

### 1.3 遥测/崩溃上报
- 无任何分析/崩溃 SDK（无包管理器，依赖仅 vendored Sparkle）；`SUSendProfileInfo=0`。**干净，无需处理**。

## 2. 更新机制（Sparkle）——「开启但指向错误源」

### 2.1 ⚠️ SUFeedURL 指向原版 MTMR 的 appcast
- Info.plist:111 `SUFeedURL = https://mtmr.app/appcast.xml`（fork 未改）。
- 实测该 feed（HTTP 200，751B）：最新版本 **0.27 / build 433**（原版 2020-11 发布）；本 fork 是 **0.27 / build 452**。
- 后果：
  1. Sparkle 版本比较 452 > 433 → **永远提示无更新**，本 fork 自己的 GitHub Releases（publish.yml）从未接入，更新通道实际是死的；
  2. **隐患**：若原版 MTMR 未来 build > 452，本 fork 会弹出「安装原版 MTMR」——错装成别的 App。
- 自动检查虽已被用户关闭（SUEnableAutomaticChecks=0），手动「检查更新」仍会命中错误 feed；实测 curl 该 URL 耗时 **6.5s**（海外域名 + 代理）。
- **方案**：`SUFeedURL` 改为 GitHub Releases 生成的 appcast（Sparkle 官方 GitHub 支持，如 `https://github.com/Tangzishun-Li/LyricsMTMR/releases/download/latest/appcast.xml`），或在 fork 不打算走 Sparkle 分发时整体移除 Sparkle 集成（AppDelegate.swift:146 的 lazy updater + 菜单项）。
- **预期收益**：消除错装风险；每次检查省 6.5s 网络往返；Sparkle XPC（Downloader/InstallerLauncher）不再注册。

### 2.2 SPUStandardUpdaterController(startingUpdater: true)
- 启动即初始化 updater 并注册 XPC 服务；在自动检查已关的现状下属「注册了但基本闲置」。开销很小（XPC 按需拉起），随 2.1 一并处理即可。

## 4. 日志——「开着但代价低」，顺手可收

- `AppLog` 全部走 `print()`（AppLog.swift:15-45）：非 os_log、无文件、**无等级门控**——info/warn/error/lyrics/touchBar/appEvent 在 Release 构建同样全量执行（仅 `debug()` 被 `#if DEBUG` 裁剪）；`@autoclosure` 只是延迟求值，字符串插值在调用点仍必然发生。
- 调用点频率低（播放切换、配置变更、错误路径），不构成持续消耗；LyricsEngine 53 处、TouchBarController 28 处均为事件级。
- **方案（可选）**：换 os_log 或按环境变量门控 info 级；**预期收益低**，非重点。

## 5. 轮询组件——按用户实时配置（~/Library/Application Support/LyricsMTMR/items.json）逐项审查

> 当前 Touch Bar 实际启用：2× stock（10s）、1× shellScriptTitledButton（5s）、1× appleScriptTitledButton（5s）、weather（默认 1800s）、lyrics、pomodoro、upnext、battery、media 控制等。TBPollItem 基类组件未启用。

### 5.1 ⚠️ CPU% 脚本组件：`top -l 2` 每 5 秒（最重的非渲染消耗）
- items.json：`shellScriptTitledButton { refreshInterval: 5, source: "top -l 2 -n 0 -F | egrep ... | awk ..." }`。
- 行为：每 5s fork `bash → top -l 2`（2 次全系统采样 ≈ 2s 子进程存活）+ egrep/awk 管道。
- 代价：**5s 周期内约 40% 的时间存在一个对全系统做采样的子进程**（top 本身就要遍历所有进程并采样两次），持续 CPU+IO，且随系统进程数放大。
- 补充：与姊妹报告 P1-4 的结论一致；但需**更正代码地图一处描述**——AppleScript/ShellScript 组件的 `execute()` 运行在后台串行队列（`mtmr.applescript` / `mtmr.shellscript`，AppleScriptTouchBarItem.swift:88 / ShellScriptTouchBarItem.swift:108），**不阻塞主线程**；代价是后台进程 fork 占空比，而非 UI 卡顿。
- **方案 A（推荐）**：该脚本改用 `ps -A -o %cpu` 单次快照求和（同 5.2 的 ps 方案，亚秒级），并把 `refreshInterval` 提到 30s（CPU% 显示无需 5s 精度）。
- **方案 B**：仅把 interval 提到 30–60s，保留 top。
- **预期收益**：消除 ~2s/5s 的子进程采样占空比，静息 CPU 再降 1–3%（视系统负载），IO 显著减少。

### 5.2 ⚠️ MEM% 脚本组件：`ps -A` 每 5 秒
- items.json：`appleScriptTitledButton { refreshInterval: 5, source: "ps -A -o %mem | awk ..." }`。
- 每 5s fork AppleScript 解释器 + ps；单次开销小，但可与 5.1 **合并为一个脚本**一次执行（ps 同时取 %cpu + %mem），间隔一并拉到 30s。
- **预期收益**：两个 5s fork 合并为一个 30s fork，进程 fork 频率降 ~12 倍。

### 5.3 ⚠️ 股票组件 ×2：10s 轮询 + 全图重绘
- items.json：2× `stock { refreshInterval: 10, showChart: true, chartMode: fenzhong(分时), chartWidth: 130 }`（sh603568 / sz002150）。
- 每 10s：HTTP 拉取（×2 只）+ **主线程**全量重绘（StockBarItem.swift:78-84 定时器 → refreshData → updateDisplay → renderStock/drawChart，463-567 行 CGContext 逐路径绘制分时图）；另有 3s 轮播 marquee 定时器（StockBarItem.swift:361-366）。
- A 股交易时段外（含夜间、周末）数据恒定，仍保持 10s 拉取+重绘。
- **方案**：按交易时段降频（非交易时段 interval 拉到 60s 或暂停定时器；`refreshInterval` 已 clamp ≥5s，需改 clamp 逻辑），或 chartMode 关闭分时图。
- **预期收益**：非交易时段省 2× HTTP/10s 与主线程全图重绘；交易时段保持现状。

### 5.4 其余组件——健康
- weather（杭州，china）：`NSBackgroundActivityScheduler` 默认 interval 1800s（ItemsParsing.swift:634 `?? 1800.0`），系统合并调度，合理。
- lyrics/pomodoro/upnext/battery：事件驱动或计时中才跑，无泄漏（定时器报告已核）。
- TBPollItem 基类：后台 compute + 主线程 apply，设计正确，当前未启用。
